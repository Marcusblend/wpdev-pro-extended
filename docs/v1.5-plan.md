# Pro Extended 1.5 "Native Complete" — build brief

This brief is written for a Claude Code session working in this repo. Do the work in the order below. Each numbered item is its own commit and comes with its own test.

## The principle

- **Pro Extended is build tooling, and nothing on a site should depend on it.** Today it registers one REST route and some CLI commands, and it adds nothing to the front end. Keep it that way.
- **It must steer every build to Cornerstone's native features:**
  - element settings
  - global colors, fonts and variables
  - components and parameters
  - Global Parameters
  - Dynamic Content
  - Twig
  - conditions
  - loopers
  - native elements and effects
- **A site build never ships site-specific PHP.** That means no plugin, no mu-plugin, no `functions.php` code, no custom shortcode and no `wp_head` output. Two recent builds shipped a "site helpers" plugin. It held a date-switched discount, price arithmetic, a copyright year, seasonal opening hours, font loading, SEO meta, JSON-LD, and behaviour scripts. Cornerstone, WordPress settings or the SEO plugin already covers every one of those.
- **Pro Extended keeps growing as Themeco ships features.** 1.5 is the current release, not the final one. When Themeco adds a native capability (a Dynamic Content group, a Twig filter, a condition rule, a looper provider, an element, a Global setting), the plugin gets coverage for it: a reference section, a recipe, a lint rule or, when nothing else will do, a tool. It never gets site-specific code. A weekly scheduled task watches Themeco releases and reports each new capability.

## Before you start

1. Update your local branch: `git fetch origin && git checkout feature/v1.4-authoring-and-verification && git pull`. The local clone is missing `605057c`, `9073fe1`, `e86de4c` and `cbf5493`.
2. Branch off it: `git checkout -b feature/v1.5-native-complete`. The v1.4 branch already contains v1.3 through merge `e86de4c`.
3. Run `php tests/unit/run.php`. Everything should pass before you change anything.
4. Follow the repo rules:
   - Keep upstream naming and structure.
   - Put no client names or client URLs anywhere in the repo.
   - Open PRs on the fork only: `gh pr create --repo Marcusblend/wpdev-pro-extended`.
   - Every tool change also updates `CHANGELOG.md` under `[1.5.0]` and the tool list in `README.md`.
5. When you need Cornerstone internals (key names, registries, the Twig environment, the importer), read Cornerstone's source on a test install over SSH. Never guess a key name. If a registry can't be read, the tool must say so in its result.

## B. Cuts

These remove about 650 lines. Each one removes hand-kept Cornerstone data or duplicates a native feature. WPML support stays; see A17, A18 and E.

1. **Header presets.** Remove `src/Recipes/HeaderRecipes.php`, the `preset` and `preset_options` inputs on `create_document`, and `tests/unit/HeaderRecipesTest.php`. The recipes hold about 40 element keys that nothing checks against the registry. The replacement is a header saved as a template, applied with the template tools or `list_prefabs`. Say so in the README.
2. **`restore_snapshot`.** Remove the tool and `SiteSnapshot::restore()`. As written it can write any option name the caller supplies. The same need is covered by:
   - Pro's Theme Options export/import (colors and fonts included since Cornerstone 7.6.0)
   - `restore_settings` for single options
   - host backups

   Keep `create_snapshot` as a read-only site inventory.
3. **`import_tco`.** Replace the hand-rolled unzip and per-entry `Template::create()` with Cornerstone's importer (`cs_import_tco`; confirm its signature in source). The current path skips the colors, fonts, components and media the native exporter bundles, and it keeps the source site's image URLs. Keep the describe-first `confirm` flow and the size limits. If the native importer can't describe an archive without importing it, keep only the describe half of `readArchive`.
4. **`Extensions::KNOWN`.** Drop the guessed class names and element types. Report what the element, Dynamic Content and looper registries contain, next to the Max package list that `features.max` already reports. Free ACF is currently reported as ACF Pro; fix that on the way.
5. **`create_component` self-check.** After a write, confirm through `ComponentScanner` that the new component is in the registry. If it isn't, restore and return an error. Today a wrong shape "saves without complaint and never appears".

## C. Native coverage

Every catalog below reads Cornerstone's live registries and is cached by Cornerstone version. If a registry can't be read, the result says so and never falls back to a hand-kept list.

1. **`get_native_reference`**: one tool with a `section` argument, so Claude Desktop's tool list stays short.
   - `dynamic_content`: what `list_dynamic_content` returns today. Keep `list_dynamic_content` as a deprecated alias for this release.
   - `twig`:
     - the enabled flag and each sub-toggle
     - the functions, filters, tests and globals registered on the site's live Twig environment (find how Cornerstone builds it, e.g. the `cs_twig_boot` hook)
     - how Dynamic Content groups map to Twig variables (`post.title`, `looper.item`, `param.x`)
   - `conditions`: rule types, their operators and value choices. Cover both element `show_condition` and document assignments (the `group`/`condition`/`value` triples such as `single:post-type`, `archive:term`), read from Cornerstone's conditions registry.
   - `loopers`: each provider's element setting keys (`looper_provider_*`) and the `{{dc:looper:*}}` fields it exposes.
   - `parameter_types`: the control types valid in `_p_json` (text, textarea, choose, select, toggle, color, image, font, group, `group[]`, and so on), and what each one outputs.
   - `regions`: the region names each document type renders.
2. **Twig.** Twig is already switched on for the four current installs.
   - Confirm that `update_theme_options` can write `cs_twig_enabled` and its sub-toggles. Add the Advanced (arbitrary PHP) sub-toggle's key to `ThemeOptionsWriter::REFUSED`, with a reason.
   - Add a `twig-syntax` code to `validate_layout`. Parse, but do not render, every string that contains `{%`, or a `{{ ` that isn't a `{{dc:` token, with the site's Twig environment.
   - Add a `twig-off` warning for Twig syntax on a site where Twig is off.
   - Read and write Twig templates (`cs_twig_templates`), so shared logic is written once and pulled in with `{% include 'cs-template:ID' %}`. Fold this into an existing tool if the storage allows.
3. **`create_document` regions.** Name each type's regions in the schema description. Make an unused region an **error**: a single layout written with a `content` region currently saves with only a warning and leaves an empty layout assigned site-wide.
4. **`set_global_js`.** Named blocks (`// pe:begin <name>` … `// pe:end <name>`), `dry_run`, backups, and `unfiltered_html` plus `global.edit_custom_js`. Refuse `<script`, `</script` and `<?`. This is the native home for the few lines of script a build can't avoid.
5. **Custom Document Assets** (Cornerstone 7.9). These are external scripts and styles, site-wide or per document. Add them to `update_document_settings` once the storage keys are confirmed in source. Accept `https` URLs only.
6. **Element facts builds had to discover.**
   - `list_elements` gains `valid_parents`.
   - The control surface gains `emits`: the properties the element always outputs and the specificity of the selector it uses. Read these from the element's style template.
   - Where the tag is free text, list the tags it accepts.
   - Add a note on the Section and Div `::before`/`::after` clearfix when `display` is set to `grid` or `flex`.

## D. Steering

1. **Replace `Server::INSTRUCTIONS`** (`src/Mcp/Server.php:59`) with the text below.
2. **Add the resource `pe://guide/native`**, a markdown recipe book, following the `ResourceInterface` pattern. Each recipe gives four things: the need, the native feature, the exact keys, tokens or Twig, and how to verify it with `render_preview`. Keep the examples generic, with no client names:
   - copyright year: `{{ "now"|date("Y") }}` or `{{dc:global:date format="Y"}}`
   - a promo that switches on a date: two elements with datetime show conditions, or a Twig ternary on values from Global Parameters
   - price arithmetic: `{{ (base * (100 - pct) / 100)|number_format(0) }}`
   - opening hours by season and weekday: Twig `date()` with PHP relative dates ("last monday of may"), always passing the site timezone
   - a thank-you message on `?sent=1`: a show condition on `{{dc:url:param key="sent"}}`
   - current nav item: a native Navigation element on a WordPress menu, using its current-item styling
   - one sticky bar in a multi-bar header
   - off-canvas or collapsed mobile navigation
   - scroll reveal with Effects scroll-enter
   - read more with an Accordion
   - filtering with Tabs, or Cornerstone Forms facets on a looper
   - self-hosted fonts: `upload_media`, then `set_fonts` with `config.customFontItems`
   - background textures: the image on a background layer, or a Global Variable holding a root-relative `url()`
   - repeating data: a Global Parameter list (`group[]`), a CSV/JSON looper, or Data Tables
   - structured data: the SEO plugin for site, breadcrumb and article schema; a footer JSON-LD block reading Dynamic Content for anything else
   - the few script lines left: `set_global_js`, or a Code element at the top of the header when the script must run before first paint
3. **New lint codes** (warnings only):
   - `custom-shortcode`: a `[tag]` whose callback is defined outside WordPress core, Pro/Cornerstone or a Themeco extension. Find where it is defined with `ReflectionFunction`/`ReflectionMethod` on `$shortcode_tags[tag]`. The message names the plugin file and suggests Twig or Dynamic Content.
   - `hardcoded-date`: a literal year beside © or "Copyright", or a literal date in promo wording ("before November 1"). Suggest the Twig or Dynamic Content equivalent.
   - `html-in-text`: a Text or Headline element whose type settings are all `inherit`, or whose `css` sets `display: contents`, and whose content holds block-level HTML. This is the "pasted design" pattern. Suggest element settings and components.

### Handshake text for D1

```
Pro Extended reads and writes Cornerstone (Pro theme) sites. Build everything with Cornerstone's own features. Never write PHP, a plugin, an mu-plugin, functions.php code, a custom shortcode or wp_head output for a site. If a need seems to require one, stop and tell the user which native feature falls short.

Use the first of these that does the job:
1. The element's own setting. get_element_schema lists the Inspector's controls and the key each one writes.
2. A global reference in that setting: "global-color:<_id>" (with alpha "global-color:<_id>:0.5"), "global-ff:<_id>", "global-fw:<_id>|fw-normal", or a Global Variable as var(--name). Read ids with list_colors and list_fonts; add them with set_colors, set_fonts and set_variables. Self-hosted fonts: upload_media, then set_fonts with config.customFontItems.
3. Reuse: a component with parameters (list_components before composing instances). Site-wide values the client edits: Global Parameters (set_global_parameters).
4. Data and logic: Dynamic Content tokens for data, Twig for arithmetic, dates and branching (get_site_info features.twig must be on). get_native_reference lists the tokens and the Twig functions and filters.
5. Visibility: show conditions; assignments for headers, footers and single/archive layouts. get_native_reference lists the rules.
6. Anything that repeats: a looper. get_native_reference lists the providers and their fields.
7. Behaviour: native elements and effects — sticky header bars, off-canvas or collapsed navigation on a WordPress menu, accordion, tabs, scroll effects, Cornerstone Forms.
8. Last resort: set_global_css for rules no setting covers; set_global_js or a Code element for the few lines of script nothing above can do.
pe://guide/native has worked recipes for common needs.

- Check every Dynamic Content token, Twig string, condition and looper with render_preview before saving, and run validate_layout.
- Every write backs up first: undo layout writes with restore_layout and settings writes with restore_settings. Never pass skip_validation or skip_backup. Run every set_* tool with dry_run: true first.
- References inside layouts: images "<attachment_id>:full", menus "menu:<term_id>", component instances {"_type": "component", "component_id": "<_c_id>", "_p_data": {...}}.
- For large documents call get_layout with summary: true first, then fetch one subtree with path.
```

## E. Tests

- **Schema parity test** (A1) and **permission coverage test** (A7), both run across every tool.
- One unit test per fix in section A.
- Update the smoke suites (`tests/smoke/`) for the removed tools and add cases for the new ones.
- **WPML test.** Run it on a throwaway install with WPML active: a Local site, or a spare WP Engine environment. Never run it on a client site. If there is no WPML licence to use, stop and ask Marcus. Cover these cases:
  - `create_translation` for a page, a post, a header, a footer, a component document and a single layout.
  - The copy's JSON decodes, it renders, and it joins the source's translation group.
  - The language fields on `list_layouts`, `list_templates` and `get_site_info` are correct.
  - A translated header is assigned to its own language.
  - A contributor can't publish a translation.
- **Twig smoke test.** It runs only on the test install, with Twig switched on for the run. `render_preview` each recipe snippet from `pe://guide/native` and assert the output: the year equals the current year; `{{ "now"|date("H:i") }}` and `date_i18n("H:i")` differ by no more than a minute from the site's time (this is how the timezone gets checked); and the date-switched promo flips when the date parameter moves.

## F. Release

1. Bump `PE_VERSION` and the plugin header to `1.5.0`, and add a `Tested up to:` line naming the newest WordPress version you tested against. The weekly watch task reads that line. Write the `[1.5.0]` changelog entry, "Native Complete", with Added / Changed / Removed / Fixed sections. List every removed tool and its replacement under Removed.
2. Open one PR on the fork. Tag `v1.5.0` after it merges.
3. Deploy the same way as before:
   - WP Engine backup checkpoint before each install.
   - The test install first; it is the only one that gets real test writes.
   - Then read-only checks and dry runs on the others.
   - Restart Claude Desktop and confirm the tool count (about 47).
   - Keep `pe_allow_skip_validation` at `0`.
4. Confirm Twig is on for each install, with the Advanced sub-toggle off.
5. Record a fresh baseline with `get_platform_baseline` `save: true` on each install. A9 and A19 change what the baseline holds, so the old one no longer compares cleanly.
6. **After 1.5.** New work comes from two places: a Themeco release the weekly watch reports as a new capability, and a build need the native reference can't meet. Each becomes a 1.x item.
